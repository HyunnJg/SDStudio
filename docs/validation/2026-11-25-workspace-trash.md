# D-063 결과·프로젝트 휴지통 검증

기준 main `99a00a0e83271b872e9cb0e0e9d7f41bbc23df9f` (PR40 검토 head7d27eef/Windows·Linux CI2/2 직접 확인 후 병합), 브랜치 `work/workspace-trash`. main 저장소/worker/IPC·생성 단일 실행권·v6 스키마와 해당 UI/검사를 변경했다. 사용자 제공 Gemini/Claude 의견을 반영했으며 새 외부 AI 재검토를 받았다는 뜻은 아니다.

## 코드/빌드

- Linux x64·Node26.13.1/npm11.20.0·기존 의존성 재사용. 재개 환경의 호스트 Node24 대신 고정 Node26 공식 아카이브를 공식 SHASUMS256과 대조해 사용했다. CI의 npm11.21.3 clean 설치와 구분한다.
- 전체 단위 **383/383** 통과(기준363+신규 저장/경합16·이동 후 sync 실패1·UI/컨트롤러3). Windows는 디렉터리 fsync를 건너뛰며 관련 하위 경로와 symlink 권한 제한은 검사 diagnostic/기존 skip으로 구분한다.
- 변경 TS/TSX13개 scoped eslint·범위 strict tsc, 수정 CJS 구문·git diff 공백 검사 통과. main.ts의 기존 전체 lint/tsc 유산을 정리하지 않았으며 전체 저장소 통과를 주장하지 않는다.
- production main/renderer build와 마지막 UI 보완 뒤 renderer 재빌드·고지 수집, Linux directory package/packaged notice 검사 통과. 식별 패키지215개·기존 원문 고지8개 미해결은 유지한다. 의존성/lock·모델 바인딩/요청 본문·암호화는 변경하지 않았다.

## 실제 Linux Electron/ASAR

새 임시 프로필·합성 PNG/가짜 토큰·루프백 ZIP만 썼다. 단일 인스턴스 잠금은 검사에서 모의이며 headless/no-sandbox는 명시적 검사 인자다. 제품 sandbox를 바꾸지 않았다.

| 선택한 통과 실행 | PID 수 | 체크 | 루프백 HTTP |
| --- | ---: | ---: | ---: |
| 휴지통/새 PID/오프라인 | 3 | 7+4+15=26 | 2 |
| 기존 기본 생성/새 PID/오프라인 | 3 | 33+4+15=52 | 3 |
| 반복 큐/새 PID/오프라인 | 3 | 10+3+15=28 | 13 |
| 참조/새 PID/오프라인 | 3 | 9+4+15=28 | 3 |
| 실제 ASAR 휴지통 | 1 | 7 | 2 |
| 합계 | 13 | 141 | 23 |

모든 선택 실행에서 실제 NovelAI0·외부 앱 요청0·renderer 오류0·정상 native 종료·원본 프로필 생성0을 확인했다. ASAR는 app.isPackaged=true·archive 실행 전후 해시 동일·프로필 격리를 확인했고 제품 ASAR의 worker를 사용했다. 하네스만 loopback inspector로 주입했다. 중간 재실행도 있었으므로 위 HTTP 수치는 이번 작업 전체의 루프백 총수라는 뜻이 아니다. 마지막 완료 문구 초기화/실패의 수동 복구 표시 보완 뒤에는 휴지통3PID26체크와 ASAR7체크를 다시 실행했고 기본/반복/참조 경로는 그 보완 전의 통과 실행이다.

확인한 동작:

- 고정 시드42로2장 생성 → 파일 이름이 서로 다름. 두 번째 실제 전송 중 main trash/restore IPC는 PROJECT_BUSY, 화면 삭제 버튼도 비활성. 추가 생성 없음.
- 캔버스에서 선택 결과 숨김 → 갤러리 개수 감소·원본 PNG 바이트 불변, 직전 되돌리기·썸네일 휴지통 복원. 휴지통 미리보기는 실제 Chromium이 디코딩한 PNG다. 직전 생성의 ‘완료’ 문구를 휴지통 오류로 재표시하지 않음.
- 중지된 저장소 응답을 **검사에서 모의 주입**해 결과2개/manifest 리비전 불변·저장 완료 표시 숨김·수동 저장 복구 버튼 노출을 확인. 실제 worker 강제 종료를 이 UI 시나리오에서 실행했다는 뜻은 아니다. 다음 명시적 정상 저장으로 오류가 지워짐. 원문 예외는 노출하지 않음.
- 현재 프로젝트 미저장 편집 → 이동 취소는 원래 위치 유지, 명시적 버리기는 저장된 manifest/PNG/이력 전체 이동. 상단 복원으로 같은 UUID/저장된 입력 재열기. 목록 휴지통 탭의 복원과 정상 탭 재열기도 통과.
- v6 결과2개 중1개를 숨긴 상태로 새 PID에서 재열기 → 정상 갤러리1개, 숨김1개, 저장된2개 PNG 원본 바이트 불변. 생성0회. 오프라인 가져오기/라이브러리도 로컬로 작동.
- 기존 단일 생성/높은 스텝 확인·취소/중복 방지·저장 실패의 새 프로젝트 보관, 반복 큐/이어가기/입력 충돌, 참조 비용 첫 확인/세션 재사용·참조 저장-only를 회귀 확인.
- 기존30개 레코드 갤러리의 초기 가시 범위 읽기(4회)·복사 후 프로젝트 캐시/URL 정리와390px·dark/light 버튼도 기존 기본 검사에서 통과. 30UUID가 같은 합성 PNG를 가리키므로 디스크 지연/메모리 피크 측정은 아니다.

## 새 단위 경계

v6의 중복/없는/경로형 숨김 UUID·boolean/리비전 거부, idempotent hide/restore·원본 바이트/이력·PNG 손상 시 숨김 유지, 입력 저장/append/전체 복사/v6 이력 복구의 숨김 유지·입력만 복제 제외, 참조 원본/파생 보존, 폴더 이동/새 store 재열기·기존 잠금/UUID 충돌·손상 manifest/크래시 잠금 보존, 이동 전 실패/이동 뒤 sync 실패의 복원 가능성, 링크/경로 거부, 실제 Node worker 비동기 호출, 신뢰 프레임 await 전후 검사, 생성↔저장 변경의 동시 진입/미저장 PNG 차단·이전 승인 무효화/예약 종료·전송0을 확인했다.

## 중간 실패와 한계

초기 기존 IPC 단위의 handler 수8개 기대를 새 계약12개로 갱신했다. 참조 회귀의 초기 한 번은 가져오기 작업이 아직 비활성인 카드에 합성 드롭을 보내 선택창을 기다리다 끝났다. 제품의 busy 검사를 완화하지 않고 실제 조작 가능 상태를 기다리도록 검사만 보완한 뒤 참조3PID28체크가 통과했다. 환경의 기존 SharpElectronLinux/dbus/빈 합성 TOKEN.txt 경고는 stderr에 남았으나 renderer 오류가 아니었다.

Windows/macOS GUI·사용자 PNG/프로젝트·OS 다운로드 창·최대120장/256MiB의 지연/메모리·실제 NAI 참조 효과/과금은 미실측이다. Windows/Linux CI의 정확한 head/run 결과는 PR에서 별도로 확인한다. 파일 선택/드롭/클릭은 renderer 합성 이벤트이며 사람의 OS 파일 창 조작이 아니다. 영구 삭제/공간 회수·고아 수거·i2i는 구현하지 않았다. [저장 계약](../WORKSPACE_TRASH.md).
