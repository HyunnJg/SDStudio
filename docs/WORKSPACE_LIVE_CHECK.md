# 새 작업실 실계정 확인 — 1장부터

갱신일: 2026-11-24 (Asia/Seoul). D-048의 V5 설정/단일 클릭 흐름 기준. 사용자는 로컬 앱 기동/생성을 보고했으나 이 브랜치의 V5 출력 실측과 구분한다.

연구 창에서의 기본 1장 성공과 **전체 앱 새 작업실의 성공**은 별개다. 다음 순서는 사용자 PC에서 실행할 확인 절차이며, 아직 실행 결과가 아니다. 코드를 검증하는 자동 테스트는 실제 계정을 호출하지 않는다.

## 전체 앱이 열리는지부터 확인

이미 전체 앱의 새 작업실이 열린다면 설치를 반복하지 않고 다음 절로 간다. `tools/nai-validation` 창만 열린 것은 전체 앱 설치 성공이 아니다.

소스에서 실행할 경우, 전체 앱 의존성이 설치된 체크아웃의 PowerShell에서 다음을 실행한다. 앱이 이미 실행 중이면 먼저 정상 종료한다.

```powershell
git switch main
git pull --ff-only
git rev-parse --short HEAD
node --version
npm run build
npm start
```

작업 중인 브랜치/파일이 있으면 덮어쓰지 않고 해당 상태를 먼저 확인한다. 현재 재현 기준은 Node 22.4.1이다. `build` 실패 뒤에는 `start`로 넘어가지 않는다. 이미 패키징된 앱을 쓰는 경우 위 명령 대신 그 앱을 실행하고 앱 버전과 소스 커밋을 구분해 기록한다.

Windows 전체 앱 설치가 아직 막혀 있다면 [Node/VS 안내](DEVELOPMENT.md#windows-전체-앱용-node-버전-준비-pr-16-후속)를 따른다. Node 22 전환만으로 기존 VS2026 탐지 오류가 해결됐다고 가정하지 않는다. 설치 복구를 위해 정상 연구 창의 Electron·lock·프로필을 지우거나 `npm audit fix --force`를 실행하지 않는다. 이 단계에서 멈추면 OS, Node/npm 버전, 실패 단계와 오류 코드만 전달하면 된다.

일반 새 실행은 온라인이다. 이전에 저장한 오프라인 선택이 있으면 **API 토큰·연결 모드**에서 온라인 저장 → 재시작을 사용한다. mock·명시적 개발 프로필·환경변수 고정 실행에서는 모드가 잠길 수 있다. 이 확인은 `start:mock`, `start:preview`, `start:isolated` 또는 연구 창으로 대체하지 않는다. 잠긴 이유가 표시되면 그대로 기록하고 일반 실행 여부를 확인한다.

## V5 Full·832×1216 1장

1. 새 작업실에서 새 입력을 만들고 평소 쓰는 프롬프트를 입력한다. V5 Full·832×1216·23스텝·가이던스7과 품질/부정 프리셋 선택을 확인한다. 이미 직접 품질/부정 태그를 넣었다면 해당 프리셋을 추가 안 함으로 바꿔 중복을 피한다.
2. 사용 조건을 NovelAI에서 확인한 뒤 **생성**을 한 번 누른다. 별도 전송 확인창은 없고 입력 저장과 요청 준비 후1회 전송한다. V5 PNG 출력 옵션은 이번에 서버 수용을 실측하지 않았으므로 응답 형식 오류도 관찰 대상으로 남긴다.
3. 성공하면 기록1건과 PNG 표시를 확인하고, 종료 후 같은 프로젝트를 다시 열어 확인한다. 결과 저장 필요라면 생성 대신 결과만 다시 저장/새 프로젝트 보관으로 이미 받은 PNG를 보존한다. 오류 뒤 같은 요청을 자동 반복하지 않는다.
4. Opus 할당량/Anlas·무료 여부는 앱이 계산하지 않는다. 결과 공유에는 성공 여부·고정 오류 코드·HTTP 상태·정제 MIME만 필요하다. 키/이미지/원문은 보내지 않는다.

## 성공한 경우에만 같은 씬 2회

1. 앞의 1장 저장·다시 열기가 성공한 뒤 온라인 상태와 토큰을 확인한다.
2. 대기열을 펼쳐 **같은 씬 하나만** 체크하고 **선택 씬마다 반복**을 `2`로 둔다. **입력 저장 후 선택 씬 예약 확인**을 누른다.
3. 확인창이 **총 2회 요청 · 이미지 2장**인지, 설정·씬·시드가 의도한 값인지 확인한다. 다른 씬까지 선택됐다면 취소하고 다시 준비한다. 같은 설정과 총 요청 수의 웹 사용 조건을 확인한 뒤 한 번 실행한다.
4. 완료되면 대기열 완료2건과 프로젝트 결과 합계3건(앞의 단일1장 포함)을 확인하고, 각 결과를 선택해 본다. 다시 열어도 3건이 유지되는지 확인한다.
5. 401/402/429/TIMEOUT·모호한 전송 실패·저장 실패가 하나라도 나면 이 확인을 멈추고 결과만 기록한다. 자동 추가 전송은 없다. 원인이 확인되지 않은 상태에서 새 예약을 만들어 실패 건을 다시 보내지 않는다. 중지는 서버 처리 취소나 미과금을 보장하지 않는다.

이번 단계는 자동 반복 실험이 아니다. 위 기본1장+반복2회 뒤에는 추가 크기·모델·캐릭터 실험을 늘리지 않고 관찰 결과로 다음 범위를 정한다.

## 공유할 관찰값

키·이미지·프롬프트·프로젝트 JSON·서버 오류 원문·절대 경로는 보내지 않는다. 화면에서 확인한 값만 적고, 없는 값은 `미표시`로 둔다.

```text
체크아웃 SHA 또는 패키지 버전:
OS / Node 버전(소스 실행일 때):
단일1장: 성공 / 오류 코드 / HTTP 상태(미표시 가능)
저장 후 다시 열기: PNG 표시됨 / 실패
반복2회: 완료 수 / 오류 코드 / HTTP 상태(미표시 가능)
결과 합계와 다시 열기: 3건 / 그 외
mediaTypeState / mediaType / 진단 httpStatus: 값 또는 파일 없음
웹 사용량 관찰: 확인한 범위만, 미측정이면 미측정
```

첫 운영 응답의 정제 MIME은 일반 Windows 포크 프로필에서 아래 파일에 **최초 1회, 최선 노력**으로 기록된다. 토큰 저장 폴더나 프로젝트 폴더와 다르다. 파일이 없더라도 생성을 반복하거나 성공 결과를 실패로 취급하지 않는다. 이미 파일이 있으면 이번 실행이 아닌 과거 최초 응답일 수 있으며, 지워서 다시 기록시키지 않는다. 별도 프로필은 실제 선택한 userData를 기준으로 확인한다.

```powershell
$mimeFile = Join-Path $env:APPDATA 'SDStudio-HyunnJg\nai-diagnostics\first-response.v1.json'
if (Test-Path -LiteralPath $mimeFile) {
  Get-Content -Raw -LiteralPath $mimeFile |
    ConvertFrom-Json |
    Select-Object version, httpStatus, mediaTypeState, mediaType |
    ConvertTo-Json
} else {
  '진단 파일 없음 — 추가 생성하지 않고 그대로 기록'
}
```

`present`는 패턴 검사를 통과한 type/subtype이고, `absent`·`invalid`에는 형식 문자열이 없다. 헤더 파라미터·원문 응답은 기록하지 않는다. MIME 형식 제한이 임의 문자열의 비민감성을 증명하는 것은 아니므로, 공유 전 선택된 필드만 확인한다. 진단 HTTP 상태는 해당 최초 응답의 관찰값이며 개별 큐 항목의 상태나 과금 증명이 아니다.
